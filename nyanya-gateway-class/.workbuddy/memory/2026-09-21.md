2. **根治**：新增 drop-in `/etc/ssh/sshd_config.d/60-nyanya-tunnel-keepalive.conf`
   （`ClientAliveInterval 15` + `ClientAliveCountMax 3`），`sshd -t` 通过后 `systemctl reload ssh`；
   `sshd -T | grep -i clientalive` 确认 `15 / 3` 生效。死会话约 45 秒内被回收、端口自动释放。
   （Ubuntu 24.04 的 unit 是 `ssh.service`；`reload` 不会踢掉已建立的会话。）
3. 本机 `tools/tunnel-to-server.ps1` 重写：捕获 ssh 的 stderr 并回显到 tunnel.log；命中
   `remote port forwarding failed` / `Address already in use`（或连续失败 ≥3 次、45 秒冷却）
   时，自动 ssh 上去按 `ss -ltnp` 找出占用者并 kill，再重连。

## 修复：群消息下行（新版 QQ 发的消息模拟器收不到）——self 过滤根因

触发：勇者验证「旧版发的新版收得到（上行已通）」，但「新版 QQ（同号）发的群消息，模拟器收不到」。

根因：`packages/gateway-core/onebot-events.js` 的 `normalizeOneBotMessage` 有一行
`if (senderId && selfId && senderId === selfId) return null` —— **丢弃所有"自己发的"消息**。
模拟器和新版 QQ 是同一个 QQ 号（self_id=2948126361），所以新版 QQ 发的群消息
（senderId===selfId）也被静默丢弃。这个过滤原本是为了防多端回显（第一方网关 `gateway/server.js`
也依赖它，且调用时**不传 selfId**）。

方案（向后兼容，不破坏第一方网关）：
1. `onebot-events.js`：self 过滤改可选 —— 加 `allowSelf` 选项（默认 false，行为不变），
   返回对象加 `isSelf` 标记。默认仍 return null；`allowSelf:true` 时放行并带 `isSelf:true`。
2. `napcat-backend.js`：
   - 构造函数加 `this._recentSentGroup = new Map()`（messageId -> {groupId,text,expiresAt}，60s TTL 惰性清理）。
   - `sendGroup` 成功后 `_rememberSentGroup(result.messageId, groupId, text)` 记下刚发出的消息。
   - `onEvent` 调 `normalizeOneBotMessage(event, { selfId, allowSelf: true })`。
   - `_onMessage`：私聊 self 消息仍 `return`（否则会变成"自己给自己发"）；群聊 self 消息
     先 `_isEchoOfRecentSend(groupId, text, messageId)` 判回显（messageId 精确匹配 + 内容时间窗口兜底），
     命中则跳过（`群消息回显已去重`），否则视为同号其他端正常推送（`群消息自同步推送`）。
3. `gateway-core/self-test.js` 补用例：`allowSelf:true` 时 self 消息返回且 `isSelf===true`。

验证：本地 `gateway-core self-test` 40 断言 + `class self-test` 全绿；已 scp 两个文件到
`/data/jar/nyanya/gateway/packages/gateway-core/` 和 `.../nyanya-gateway-class/core/`，
重启后 PID 133922，NapCat 已重连、镜像刷新正常（self=2948126361 好友4 群4）。
**待真机验证**：新版 QQ 发的群消息 → 模拟器应能收到；模拟器自己发的 → 不重复回显。

## 排查：群历史回放「没了」= 回放水位 TTL 误判「重启」为「重连」（根因已定位）

触发：勇者「现在历史消息预览没了，聊天框空了，但聊天记录是有的」。排除了 self 过滤改动（无关）。

现象（服务器日志，全程实证）：17:20 登录后 `private_history_replayed` 触发（7 条、fresh=1），
但**同一次登录没有 `group_history_replayed`**；客户端 17:21:12 手动请求 `bid=204`（群窗口空，
只能手翻 WAP 群聊天记录）。17:08 及之前每次登录群回放都正常（`messages:10`）。

根因（`core/replay-cursor.js` 的 TTL 折中，`replayCursorTtlMs=600000`=10 分钟）：
1. 17:08 登录 → 群回放全量 10 条 → 水位 `afterId=12`、`at=17:08:48`。
2. 17:11 客户端**重连**（peer 从 `.193` 变 `.129`，无 login_ok）→ 触发第二次 `group_sync`
   → 增量回放 1 条（id13「回显test」）→ 水位刷成 `afterId=13`、`at=17:11:27`。
3. 17:20 客户端**重启登录**（距 17:11 仅 8 分 57 秒 < 10 分钟 TTL）→ 水位未过期 →
   `recentGroupMessages(..., afterId=13)` 增量为空 → `messages=0` → 不打日志、群窗口空。
   私聊正常的原因：私聊水位在 17:08 推进、17:20 已过期（12 分钟），所以 fresh 全量回放；
   群聊水位被 17:11 重连刷新过，17:20 没过期，所以增量空。**两者不对称，恰好暴露了缺陷。**

本质：老客户端**群窗口是内存、重启即空**（`hq.java`），需要「重启后全量补历史」；但水位
TTL 无法区分「掉线重连」和「重启」（协议层长得一样），TTL=10 分钟太长，把 8 分钟前的重启
误判成重连，只推不存在的增量。这跟最近的 self 过滤改动无关，是既有折中边界，服务器上
17:08→17:11→17:20 的节奏恰好踩中。

**修复（已实施，方案 A）**：勇者拍板「A」。服务器 `config.json` 的 `replayCursorTtlMs`
`600000 → 120000`（2 分钟），`systemctl restart` → active，NapCat 已重连、镜像刷新正常
（self=2948126361 好友4 群4）。代价：短时间重连（网络抖动）也会全量重推最近 limit 条，可接受。
更彻底方案（未做）= 群/私聊分开水位 TTL（群短私聊长），需改 `server.js` 创建两套 cursors。
验证：勇者重开模拟器登录，群历史应全量回放（最近 10 条）。
