# 异地部署：原理与坑（服务器侧）

> ⚠️ **操作步骤请以 `操作手册.md` 为准**（那是操作步骤的唯一权威，服务器 + 本机全步骤都在里面）。
> 本文保留「为什么这么部署」的原理、踩过的坑、以及已知问题与边界，**不再重复操作步骤**。
> 与操作手册冲突时，以操作手册为准。

---

## 1. 为什么 NapCat 留家里

NapCat 本质是在跑 QQ 客户端。把 QQ 登录在数据中心 IP 上，对腾讯来说是高风险 IP，实际常见表现是：
登录要额外验证、频繁掉线、甚至冻结。

NapCat 留家里走家宽的住宅 IP，风控友好得多。云服务器只承担「老手机接入」这一件事。

---

## 2. 目录结构是硬约束（相对路径）

代码里所有跨包引用都是**相对路径**：

| 文件 | 引用 |
|---|---|
| `server.js:17` | `require('../packages/gateway-core')` |
| `core/napcat-backend.js:7` | `require('../../packages/onebot-adapter')` |
| `core/napcat-backend.js:18` | `require('../../packages/gateway-core')` |

所以 `packages/` **必须是 `nyanya-gateway-class/` 的兄弟目录**，不能只把 `nyanya-gateway-class` 单独拷过去。

好消息是没有任何第三方 npm 依赖（只用 Node 内置模块），**不需要 `npm install`**，传上去就能 `node server.js`。

## 3. 打包脚本的坑（tools/package-release.ps1）

发布打包用根目录 `npm run release`。脚本会自动排除 `config.json`、数据目录、日志、JAR，并断言没把
本地 secret 带进包里。这里踩过四个坑：

### 3.1 `nyanya-data-backup-<时间戳>/` 没被排除

排除清单只写了 `nyanya-data`，备份目录不匹配，于是**真实聊天库和日志会被打进发布包**。
已改成通配符规则（`nyanya-data*`），`Assert-SafeRelease` 的禁止文件正则也改成 `nyanya-data[^/]*`，
并补上了 `.git` / `.workbuddy` / `*.iml`。

### 3.2 secret 检查误报（词边界）

若 `deviceToken` 是较短的纯数字口令，很容易正好是 `docs/零基础教程.md` 里示例数组 `[123456789, 987654321]`
中数字串的前缀，纯 `Contains` 判定就会把示例文档误当成泄露点。已改为要求命中处**前后都不是字母数字**
（独立 token 才算），避免短 token 撞上前缀。

### 3.3 自测脚本撞 secret 检查

`self-test.js` 里写死的示例发送者 QQ 号正好等于 `onebotToken`，`legacy/self-test.js` 里写死的 32 位
协议字段正好等于当时的 `deviceToken`。**发布包现在不再包含自测脚本**（`self-test.js`、`legacy/self-test.js`、
`tests/`），`tools/release-assets/class-package.json` 里对应的 test 脚本也一并去掉。

### 3.4 ⚠️ 脚本必须保持纯 ASCII（最隐蔽的坑）

PowerShell 5.1 把无 BOM 的 `.ps1` 按 GBK（zh-CN 是 ANSI）读，中文注释里非 ASCII 字节数为奇数时，
末尾残缺字节会**吃掉下一行的换行**，让紧随其后的那行代码**静默变成注释** —— 不报错、不警告、只是不生效。

真实踩过：一个中文注释把 `if ($Normalized -like $bare)` 整行吞掉，通配符排除规则静默失效（精确规则
还正常，非常难排查）。脚本顶上已加**纯 ASCII 自检**，违反会直接抛错。所以脚本里引用中文文档名时，
必须用**码点拼接**（`-join [char[]](0x...)`）构造，不能直接写中文。

## 4. 登录鉴权与密码（deviceToken）

- 登录鉴权是 `MD5(latin1(密码))` 摘要比对（`legacy/store.js` 的 `digestPassword`），客户端自己算好发过来
  （`store.authenticate(uin, login.passwordDigest)`）。**不是明文，但摘要可重放**（无 nonce/salt）。
- **手机登录的「密码」= 服务器 `config.json` 里的 `deviceToken`，不是 QQ 密码。**
- 改 `deviceToken` = 改老客户端登录密码：改 `config.json` → `chown nyanya:nyanya` + `chmod 600` →
  `systemctl restart nyanya-gateway`。重启后网关会把库里的设备账号口令同步成新 token
  （日志 `设备账号密码已同步为 config 中的 token`）。
- 客户端登录失败显示的「付费用户余额不足 错误ID=31」是 **2011 版误导文案**，真实含义就是本次登录被拒
  （`login_rejected reason="bad_credentials"`），跟余额无关。
- 媒体 ID 是 `crypto.randomUUID()`（`legacy/media-service.js`），不是自增，13981 全开也枚举不出别人的图。

## 5. 隧道方案演进：SSH 反向 → frp

早期用 SSH 反向隧道（`ssh -R 3001:127.0.0.1:3001`），后因家庭宽带 NAT 周期性刷新导致**反复断线**，
切换到 frp。

SSH 反向隧道的两个已知缺陷（现已不用，仅作历史记录）：

1. **僵死端口占坑**：网络瞬断后 ssh 客户端退出，但服务器上那个无 TTY 的 `sshd: root` 子进程没意识到
   对端已死，**继续占着 `127.0.0.1:3001`**；下一次 `-R` 因端口被占当场失败，
   `ExitOnForwardFailure=yes` 让 ssh 直接 exit 255，永远重连不上（`tunnel.log` 刷 attempt 上百次）。
2. **吃 NAT 掐断**：家庭宽带的 NAT/运营商周期性刷新连接表，会掐断 ssh 长连接，需要外部脚本重试。

frp 的优势：frpc 内部有**自动重连**，断线后自己重试，网络恢复自动接上，不用外部脚本盯。且 frpc 是
主动出站，家里 IP 随便变都无所谓。

## 6. 已知问题与边界

### (1) `loginPublicHost` 只认 IPv4 字面量

登录响应报文里 IP 字段固定 4 字节（`legacy/protocol.js` 的 `ipv4ToBuffer()` 校验）。规则：

- 写了合法 IPv4 → 用该值，写进报文偏移 +0 和 +46 两处
- 留空，或写了域名 / IPv6 / 越界数字 / 前导零 / `0.0.0.0` → 回退自动探测；「非空但不合法」会额外打一条 error 日志

它**只影响登录响应报文，不改变手机实际连的地址**——真正决定连接目标的是 JAR 常量池里
`patch-client.ps1 -ServerAddress` 写进去的值。

### (2) Symbian 路线在这种部署下不适用

`启用塞班路由.bat` 的原理是把手机 Wi-Fi 默认网关改成电脑局域网 IP，靠本机路由劫持流量，
前提是「网关和手机在同一局域网」。上云之后这条路走不通。**结论：服务器部署只对 J2ME / MobileQQ
这条路线有效。**

### (3) 隧道断线不补发

家里 NapCat 或 frpc 掉线时，网关失去 OneBot 连接。恢复后网关自动重连 WS，但**掉线期间的消息不会补发**
（群消息本来就没有离线补发机制）。

### (4) 流量

收图（NapCat → 手机）走 `13981`，发图（手机 → QQ）走 base64 经网关中转，两条都吃服务器的带宽和流量包。
图片多的话注意套餐。

### (5) 明文协议暴露面

即使加了 IP 白名单，14000 上的老 QQ 协议仍然是明文、无加密、无鉴权。IP 白名单是唯一的门锁。

### (6) NapCat 不回推「自己账号在别的端发的消息」（self 消息）

`reportSelfMessage:true` 只对「通过 NapCat API 发的消息」可能回显，**覆盖不到其他端（新版 QQ 同号）
直接发的消息**。判据：NapCat 日志里 self 消息一律「发送→」，从不「接收←」。⇒ 同号多端同步在
当前 NapCat 单号架构下做不到，网关侧无解。**改网关前先确认上游到底推不推该事件，别假设。**
